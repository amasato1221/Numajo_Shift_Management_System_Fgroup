## 6. コンフリクトを防ぐ決まり

コンフリクトは「2人が同じファイルの近い行を同じ時期に変える」と起きます。そこで、**1つのファイルを変えるのは1人だけ**にします。

### 6.1 ファイルの持ち主

持ち主だけがそのファイルを変更します。ほかの人がそのクラスのメソッドを使いたいときは、持ち主に頼んで足してもらいます（自分では足さない）。

| 持ち主 | ファイル |
| --- | --- |
| 新井 | ①・④a・④b のすべて。service：NotificationService、StoreSettingService、NotificationSettingService、CalendarFeedService、RequiredStaffService、StaffHomeService、ShiftCalendarService、ShiftTableService、AbsenceService、DashboardService、ManagerAccountService、BackupService・BackupRecorder、OperationLogService（③のマージ後）。controller：GlobalModelAdvice、NoticeController、StaffHomeController、StaffShiftController、StaffSettingController、ManagerHomeController、ManagerRequiredStaffController、ManagerAbsenceController、ManagerSettingController、Admin で始まる4つ。scheduler：DeadlineNotificationScheduler |
| 川端 | ②・③のすべて。service：UserService、StaffService、SkillService、PeriodService、ShiftRequestService、AssignmentService、ShiftWarningService、ChatService。controller：RootController、LoginController、AccountController、CalendarFeedController、StaffRequestController、StaffChatController、ManagerStaffController、ManagerSkillController、ManagerPeriodController、ManagerChatController。scheduler：PeriodScheduler |
| 画面の担当 | その画面のテンプレート（`templates/…/xxx.html`）、form、その画面で初めて使う dto |
| クラスの持ち主 | そのクラスのテスト（`src/test/java/…/XxxTests.java`） |

form・dto を別の画面でも使うときは、最初に作った人が持ち主です。あとから使う人は変えません。

### 6.2 共有のファイルは共通部分で全部作り、あとから変えない

次のファイルは全員が使うので、共通部分（①〜④b）で設計書の全文を入れ、そのあとは変えません。どうしても変えるときは、92_Git運用規約 6章の流れで新井が設計書を直し、新井が1つの小さなプルリクエストで変えます。マージされたら、全員がすぐに自分のブランチへ `main` を取り込みます。

`pom.xml`、`application.yml`、`messages.properties`、`db/migration/V1・V2`（変えずに `V3__…` を足す。40_DB設計書 7章）、`SecurityConfig`、entity、repository、`layout/`・`fragments/`、`app.js`

### 6.3 app.css の区切り

自分で書く CSS は `app.css` の1ファイルだけです（91_コーディング規約）。④b で、画面IDごとの区切りのコメントを画面一覧の順に入れておき、各自は**自分の画面の区切りの中だけ**に書きます。区切りの間は空行を1行あけます。

```css
/* ===== 共通（④b。新井） ===== */
…

/* ===== SB-01 ホーム（新井） ===== */

/* ===== SB-02 シフトカレンダー（新井） ===== */

/* ===== SB-03 シフト希望提出（川端） ===== */
```

### 6.4 ブランチの使い方

| 決まり | 理由 |
| --- | --- |
| 1つのブランチは1画面まで（92_Git運用規約 2.1）。2コマ以内にプルリクエストを出す | 長く離れているほど `main` との差が大きくなる |
| 毎コマの最初に、自分のブランチに `main` を取り込む：`git pull origin main` | 小さいうちにコンフリクトを見つける |
| 5.2 の「までにマージ」は必ず守る。間に合わないときは、その前のコマで相手に伝える | 相手がその Service を使えずに止まる |
| Eclipse の書式設定（96_環境構築手順書 4章）をそろえ、保存アクションは「編集した行」だけにする | 他人の行の空白や並び順が変わると、関係のない行でコンフリクトする |
| 改行は LF（`core.autocrlf=false`、確認スクリプトの E06） | 改行コードの違いで全行が変更扱いになる |
| 機能のブランチで `docs/` を変えない（設計書の修正は 92_Git運用規約 6章の流れ） | 設計書は新井だけが直す |

### 6.5 コンフリクトが起きたとき

1. 自分のブランチで `git pull origin main` を実行し、コンフリクトしたファイルを Eclipse で開いて直す。
2. 相手のファイルの部分は、自分で決めずに持ち主に確認する。
3. 直したら Eclipse で全体をビルドし、`mvnw.cmd test` を通してからプッシュする。
4. `rebase`・`push --force` は使わない（92_Git運用規約 4.1）。
