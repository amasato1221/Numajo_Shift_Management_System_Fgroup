## 1. 各画面の詳細設計書の読み方

画面ごとの詳細設計書（20-SC-01〜20-SA-04、20-IC-01）は、次の順で書いています。

1. 概要（画面ID・URL・権限・テンプレート・コントローラー・関係する機能ID）
2. 画面項目（No.・項目名・種類・HTMLのname／表示元・初期値・入力チェック・備考）
3. 処理（初期表示・各ボタン）…番号付きの手順。上から順に実装する
4. 使うクラスとメソッド（30_クラス設計書と同じ名前）
5. メッセージ（93_メッセージ一覧のコード）
6. 操作ログ
7. テストの観点（97_テスト計画書でテストケースにする）

**手順の書き方：** 「→」は「その結果を使って次へ」、【エラー】は業務エラーとしてその場で処理を止めることを表します。

## 2. コントローラーの書き方（全画面共通）

### 2.1 GET（画面表示）

```java
@GetMapping("/staff/requests")
public String show(@RequestParam(required = false) Long periodId,
                   @AuthenticationPrincipal LoginUser loginUser, Model model) {
    // 1. Serviceから表示用DTOを受け取る
    // 2. model.addAttribute で画面に渡す（属性名は各詳細設計書のとおり）
    // 3. テンプレート名を返す
    return "staff/requests";
}
```

- ログイン中の利用者は `@AuthenticationPrincipal LoginUser loginUser` で受け取ります。`SecurityContextHolder` を直接使うのは security パッケージの中だけです。
- フォームを使う画面は、GET でも `model.addAttribute("xxxForm", form)` を必ず入れます（`th:object` が null にならないように）。

### 2.2 POST（更新）

```java
@PostMapping("/staff/requests")
public String submit(@Validated @ModelAttribute("shiftRequestForm") ShiftRequestForm form,
                     BindingResult bindingResult,
                     @AuthenticationPrincipal LoginUser loginUser,
                     Model model, RedirectAttributes redirectAttributes) {
    if (bindingResult.hasErrors()) {
        // 画面の再表示に必要な値を入れ直してテンプレートを返す
        return "staff/requests";
    }
    try {
        service.submit(...);
    } catch (BusinessException e) {
        redirectAttributes.addFlashAttribute("errorMessage", e.getMessageCode());
        redirectAttributes.addFlashAttribute("errorArgs", e.getArgs());
        return "redirect:/staff/requests?periodId=" + form.getPeriodId();
    }
    redirectAttributes.addFlashAttribute("successMessage", "I1302");
    return "redirect:/staff/requests?periodId=" + form.getPeriodId();
}
```

- フラッシュ属性の名前は `successMessage`・`warningMessage`・`errorMessage`（値はメッセージコード）と、`successArgs`・`warningArgs`・`errorArgs`（`Object[]`、なくてもよい）に統一します。
- `fragments/messages.html` が `#{${successMessage}(${successArgs})}` の形で表示します。

### 2.3 権限の二重チェック

URLの権限は Spring Security で判定しますが、さらに **「自分のデータか」** を Service で確認します。例：バイトは自分の希望しか変えられない、店長は STAFF 以外のユーザーを SM-03 で編集できない。違反は `ResourceNotFoundException`（404）にします（存在を教えないため）。

## 3. 共通レイアウト（layout/base.html）

### 3.1 構成

```
┌───────────────────────────────────────────────┐
```

## 4. シフトの表示部品（fragments/shift-badge.html）

| 表示 | 条件 | 見た目（CSSクラス） | 中身 |
| --- | --- | --- | --- |
| 日勤 | 公開済みの割当で、枠＝日勤 | `.badge-day`（緑 #00843D、白字） | ☀ |
| 夕勤 | 公開済みの割当で、枠＝夕勤 | `.badge-evening`（オレンジ #F58220、白字） | ☾ |
| 時間指定 | 公開済みの割当で、枠なし | `.badge-time`（緑→オレンジのグラデーション、白字） | 重なる枠のアイコン（☀、☾、☀☾）＋時間（`13-22`） |
| 未確定 | 未公開の期間で、自分が○か時間指定を出している | `.badge-pending`（グレー #C9CFD3、濃い灰の字） | 同じアイコン・時間 |
| 欠勤 | 割当の状態が ABSENT | `.badge-absent`（白地、赤い取り消し線） | 同じアイコン・時間 |

**「未確定」の意味：** 公開前の店長の割当（下書き）はバイトに見せません。その代わり、自分が出した希望（○・時間指定）をグレーで表示します。

部品は `th:replace="~{fragments/shift-badge :: badge(${b})}"` で使い、`b` は `ShiftBadge` レコード（30_クラス設計書）です。

## 5. 入力チェックの共通ルール

- 入力チェックはフォームクラスの Bean Validation で行い、メッセージは `message = "{E2201}"` のように 93_メッセージ一覧のコードで書きます。
- 複数の項目にまたがるチェック（開始＜終了など）と、DBを見ないとわからないチェック（重複など）は Service で行い、`BusinessException` を投げます。
- 前後の空白は取り除きます（`GlobalModelAdvice` の `@InitBinder` で `StringTrimmerEditor(true)` を登録。空文字は null になる。30-06）。
- 文字数は Java の `String#length()`（UTF-16の単位）で数えます。DBの VARCHAR(n) は文字数なので、絵文字を含む場合は length が多めに出ますが、問題ないものとします。
