## 1. この画面を作った理由

01_仕様書 4.1(4)「期限を過ぎたら、変更は店長に連絡して店長が直す」を実現するための画面です。03_画面遷移図 第1.2版にはないため、基本設計で追加しました。SM-06 の割当表の行の見出しにある「希望を直す」リンクから開きます。

## 3. 処理

### 3.1 初期表示（GET /manager/periods/{id}/requests/{userId}）

1. `ShiftRequestService#getProxyPage(periodId, staffUserId)`
   1. 期間がない → 404。
   2. ユーザーがない・role が STAFF でない → 404。
   3. 期間の status が OPEN・CLOSED 以外（PUBLISHED）→【エラー】E2612（フラッシュ errorMessage で `redirect:/manager/periods/{id}`）
   4. `RequestPageView` を SB-03 の 3.1 の 1-3〜1-7 と同じ手順で作る（`userId` は対象のバイト）。`editable` は常に true（そのため `submissionState` は CLOSED にならない）。
2. model：`page`、`shiftRequestForm`、`timeOptions`、`staff`（氏名）。`manager/request-proxy` を返す。

### 3.2 保存（POST /manager/periods/{id}/requests/{userId}）

1. 入力チェック（`@Validated`）。エラー → 3.1 の値を入れ直し、送られたフォームのまま再表示。
2. `form.periodId` が URL の `{id}` と違う →【エラー】E1301
3. `ShiftRequestService#proxySubmit(periodId, staffUserId, form, operatorId)`（`@Transactional`）
   1. 3.1 の 1-1〜1-3 と同じチェック（期限は**見ない**）。
   2. `validateDays(period, form.days, qualifiedSlotIds(staffUserId))`：SB-03 の 3.2 の 2-3・2-4 と同じチェック（E1302〜E1308）。
   3. 保存：SB-03 の 3.2 の 3 と同じ（希望を消して入れ直し、`request_submissions` を今の日時で UPSERT）。
   4. 操作ログ `REQUEST_PROXY_UPDATE`（target：`user:{staffUserId}`、detail：`period={periodId}`）。
4. `redirect:/manager/periods/{id}`、フラッシュ I2610（引数：氏名）。
5. 業務エラー → フラッシュ errorMessage／errorArgs で `redirect:/manager/periods/{id}/requests/{userId}`。

**注意：**

- 希望を直しても、すでにある割当は変えません（割当は SM-06 で店長が直す）。
- 本人へのお知らせは送りません（店長が本人と連絡を取ったうえで直すため）。

## 8. テストの観点

| No. | 観点 | 期待結果 |
| --- | --- | --- |
| 1 | OPEN の期間（期限内）で保存 | 保存され、提出済みになる。操作ログが1件 |
| 2 | CLOSED の期間（期限後）で保存 | 保存される（期限は見ない） |
| 3 | PUBLISHED の期間で開く・保存 | E2612 で SM-06 へ |
| 4 | 店長・管理者の userId | 404 |
| 5 | 対象のバイトに夕勤の職能がない | 夕勤は「職能なし」。OK を送ると E1302 |
| 6 | 未提出の人を保存 | `request_submissions` ができ、SM-06 の「未提出」バッジが消える |
| 7 | hidden の periodId を書き換え | E1301 |
| 8 | 保存後の割当 | 変わらない |
| 9 | 本人のお知らせ | 増えない |
