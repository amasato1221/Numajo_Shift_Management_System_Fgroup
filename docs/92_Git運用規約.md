## 2. ブランチ

### 2.1 ブランチの種類

| ブランチ | 作るもと | 使い方 | 名前の例 |
| --- | --- | --- | --- |
| `main` | － | いつでもビルドとテストが通る状態。**直接プッシュしない** | `main` |
| 機能 | `main` | 画面・機能を1つ作る | `feature/SB-03-request-submit` |
| 設計書 | `main` | 設計書を直す | `docs/fix-SM-06-warning` |
| 不具合 | `main` | テストで見つかった不具合を直す | `fix/SM-07-recipients` |
| 共通部分 | `main` | 画面に属さないクラス（config・entity・repository・util など） | `feature/common-entity` |

- 名前は `種類/画面ID（ないときは common）-英小文字の短い説明`。単語は `-` でつなぎます。日本語は使いません。
- 1つのブランチで作るのは、20_詳細設計書の1ファイル分（1画面）までにします。大きくなるとレビューできないためです。
- マージしたブランチは自動で消えます（GitHub の設定「Automatically delete head branches」）。

### 2.2 作る順番

画面より先に共通部分を作ります。後の画面は前の部分を使うので、この順番でマージします。

| 順 | ブランチ | 内容 | 設計書 |
| --- | --- | --- | --- |
| 1 | `feature/common-project` | pom.xml、Maven Wrapper、application.yml、起動クラス、Flyway の V1・V2 | 10 の7・8章、40 |
| 2 | `feature/common-entity` | constant、entity、repository | 30-01〜30-03 |
| 3 | `feature/common-security` | security、SecurityConfig、OperationLogService、SC-01 | 30-04、20-SC-01 |
| 4 | `feature/common-layout` | layout・fragments、app.css、app.js、GlobalModelAdvice、GlobalExceptionHandler、エラー画面、util | 20-00、30-06、30-08 |
| 5 | 画面ごと | SC → SB → SM → SA → IC、最後に scheduler | 20 の各ファイル、95 |

3以降は、前の番号がマージされてから作り始めます（4と5の一部は並行してよい）。

### 2.3 main を守る GitHub の設定

`main` には GitHub のルールセット「main保護」を付けています。設定を変えるのは新井だけです。

| 設定 | 内容 |
| --- | --- |
| 直接プッシュ | 禁止（新井も含めて全員）。変更は必ずプルリクエストで入れる |
| マージできる人 | 新井だけ（Restrict updates。例外は「Repository admin」の「プルリクエスト経由のときだけ」） |
| 承認・テスト | GitHub の設定では必須にしていない。新井がマージの前に確かめる（5章） |
| マージ方式 | 「Squash and merge」だけ |
| 強制プッシュ・`main` の削除 | 禁止 |

## 3. コミット

### 3.1 コミットメッセージ

```
種類: 何をしたか（日本語、50文字まで）

なぜそうしたか・補足（あれば。1行空けて書く）

関係する設計書：20-SB-03
```

| 種類 | 使うとき |
| --- | --- |
| `feat` | 機能を足した |
| `fix` | 不具合を直した |
| `docs` | 設計書・README を直した |
| `test` | テストだけを足した・直した |
| `refactor` | 動きを変えずに書き方を直した |
| `chore` | ビルド設定・.gitignore など |

例：

```
feat: シフト希望の提出と取り消しを作成

期限の判定は状態と日時の両方で行う（10_基本設計書 6.1）。

関係する設計書：20-SB-03
```

### 3.2 コミットの決まり

- 1つのコミットには、1つのまとまった変更だけを入れます。
- コミットする前に、Eclipse で全体をビルドし（エラーが0）、自分が触ったクラスのテストを実行します。
- `git add .` を使う前に `git status` で、入れてはいけないファイル（1.2）がないか確かめます。
- パスワードや `logo.png` を誤ってコミットしたときは、プッシュせずに新井に連絡します（プッシュしてしまった場合も、すぐに連絡します。公開リポジトリなので、パスワードは変更が必要です）。

## 4. プルリクエスト

### 4.1 流れ

1. `main` を最新にする：`git switch main` → `git pull origin main`
2. ブランチを作る：`git switch -c feature/SB-03-request-submit`
3. 実装・テスト・コミット
4. プッシュする：`git push -u origin feature/SB-03-request-submit`
5. GitHub でプルリクエストを作る（宛先は `main`）
6. 新井の確認を受け、指摘があれば直してプッシュする
7. 新井が確認して「Squash and merge」でマージする（ブランチは自動で消える）。新井以外はマージできない（2.3）
   - マージの画面には「Merging is blocked」と出ますが、設定どおりです。新井は「Merge without waiting for requirements to be met (bypass rules)」にチェックを入れてマージします

作業中に `main` が進んだときは、自分のブランチに `main` を取り込みます：`git pull origin main`（マージ）。**ほかの人とも使っているブランチで `rebase` や `push --force` をしてはいけません。**

### 4.2 プルリクエストの書き方

タイトルはコミットメッセージの1行目と同じ形（`feat: シフト希望の提出と取り消しを作成`）。本文は次の形にします。

```markdown
## 概要
（何を作ったか・直したか）

## 関係する設計書
- 20-SB-03 シフト希望提出

## 確認したこと
- [ ] Eclipse でビルドエラーが0
- [ ] `mvnw.cmd test` がすべて成功
- [ ] JaCoCo で、追加したクラスの命令網羅（C0）・判定条件網羅（C1）が基準どおり（97_テスト計画書 2章）
- [ ] 条件網羅・複数条件網羅の組み合わせ表を作り、すべての組み合わせをテストした（97_テスト計画書 3章）
- [ ] 設計書の「テストの観点」をすべて確かめた
- [ ] 画面を PC・スマホの幅で確かめた（画面を変えたとき）

## 画面のスクリーンショット
（画面を変えたときだけ）

## 設計書と違うところ
なし（ある場合は、先に設計書を直すプルリクエストを出す。6章）
```

## 5. レビュー

| 項目 | 決まり |
| --- | --- |
| レビューする人 | 新井（すべてのプルリクエスト）。ほかの班員が見てコメントしてもよい |
| 見ること | (1) 91_コーディング規約 7章の「してはいけないこと」 (2) 設計書どおりか（クラス名・メソッド名・URL・メッセージコード） (3) テストが 97 の基準を満たすか |
| コメントの書き方 | 直してほしいことは「〜してください（理由）」、好みの問題は「（任意）」と付ける |
| 承認 | 新井が確認してマージすることを承認とする（GitHub の「Approve」は押さなくてもよい）。指摘がすべて直るまでマージしない |
| マージする人 | 新井だけ。新井が作ったプルリクエストも、新井が確かめてマージする |
| マージしてよい条件 | すべての指摘が直っている、テストがすべて成功している（GitHub の設定では必須にしていないので、新井がマージの前に確かめる） |

## 6. 設計変更の流れ

実装中に、設計書が間違っている・足りない・決めていないところを見つけたとき：

1. 実装を止めて、新井に連絡します（何がどう困るか、案があれば案も）。
2. 新井が決めたら、`docs/…` のブランチで設計書を直し、改版履歴に1行足します（版は第1.1版、第1.2版…と上げる）。
3. 設計書のプルリクエストを `main` にマージします。
4. 実装のブランチに `main` を取り込み、直った設計書どおりに実装します。

**設計書に書いていないことを、実装で勝手に決めてはいけません**（10_基本設計書 1章）。

## 7. タグ

| タグ | いつ付けるか |
| --- | --- |
| `v0.1.0` | 共通部分（2.2 の1〜4）がそろったとき |
| `v0.9.0` | 全画面ができ、結合テストを始めるとき |
| `v1.0.0` | 総合テストが終わり、発表に使う版 |

タグは新井が `main` に付けます：`git tag -a v1.0.0 -m "発表版"` → `git push origin v1.0.0`。
