## 1. 目的と体制

### 1.1 目的

シフト管理システムが設計書どおりに動くことを、決まった基準（2章）で確かめます。基準を満たさないものは発表に使う版（`v1.0.0`。92_Git運用規約 7章）に入れません。

### 1.2 だれが何をするか

| 役割 | 担当 | すること |
| --- | --- | --- |
| テスト計画（この文書）、テストの観点（20_詳細設計書） | 新井 | 何をどこまで確かめるかを決める。不具合を直すか、設計を直すかを決める |
| 単体テスト・結合テストのコード | 実装した人 | 画面・クラスを作るときに、同じプルリクエストでテストのコードも書く（2章の基準を満たす） |
| テストの実行と記録 | 栗原さん | 6章の手順で全テストを実行し、7章の様式で結果を記録する。総合テスト（5章）を手で行う |
| 不具合の修正 | 実装した人 | 7.2 の流れで直す |

### 1.3 テストの種類

| 種類 | 何を確かめるか | 方法 | いつ |
| --- | --- | --- | --- |
| 単体テスト | 1つのクラス（Service・util・security など）の分岐と計算 | JUnit 6 ＋ Mockito（DB を使わない）。Repository の `@Query` は `@SpringBootTest` ＋テスト用 DB | 実装と同時。プルリクエストごと |
| 結合テスト | URL を開いてから DB に入るまでの流れ、権限、入力チェック、画面に出る値 | `@SpringBootTest` ＋ `MockMvc` ＋テスト用 DB `shift_test` | 実装と同時。プルリクエストごと |
| 総合テスト | 実際のブラウザ・端末で、業務の流れが最後まで通るか | 手で操作（5章のシナリオ） | 全画面がそろったあと（`v0.9.0` 以降） |

## 2. 合格の基準（網羅の基準）

### 2.1 4つの網羅

すべての判定（`if`、`? :`、`while`、`for` の条件、`&&`・`||`、`switch`、Stream の `filter` の条件）について、次の4つを満たすテストを書きます。

| 網羅 | 意味 | 確かめ方 | 基準 |
| --- | --- | --- | --- |
| 命令網羅（C0） | すべての命令を1回以上動かす | JaCoCo の「Instructions」 | 100% |
| 判定条件網羅（C1、分岐網羅） | すべての判定で、真と偽の両方を1回以上通す | JaCoCo の「Branches」 | 100% |
| 条件網羅（C2） | 判定の中の**1つ1つの条件**（`a && b` の `a` と `b`）が、真と偽の両方になるようにする | 組み合わせ表（3.2）を作り、表のすべての行をテストにする | 表の行が全部テストにある |
| 複数条件網羅（MCC） | 1つの判定の中の条件の**真偽の組み合わせすべて**（条件が n 個なら 2ⁿ 通り）を試す | 同じ組み合わせ表で、全部の組み合わせを書く。ありえない組み合わせは理由を書いて除く | 表の行が全部テストにある |

- JaCoCo の Branches は、`a && b` の短絡評価も1つの分岐として数えるため、C1 と C2 の一部を表します。ただし**組み合わせ（MCC）は測れない**ので、3.2 の表で確かめます。
- 100% にできない命令・分岐（例：起こりえない例外の `catch`）は、テストの結果（7.1）の「除外」欄に、場所と理由を書いて新井の確認を受けます。

### 2.2 対象と除外

| パッケージ | 基準 | 理由 |
| --- | --- | --- |
| service、security、util、exception、scheduler、constant、controller | 2.1 の4つすべて | 業務ルールと画面の流れがあるため |
| entity、form、dto | 除外（JaCoCo のレポートでは見ない） | Lombok が作るメソッドと record だけで、判定がない。form の入力チェックは controller の結合テストで確かめる |
| config | 除外（ただし SecurityConfig は 94_セキュリティ設計書 6章の結合テストで確かめる） | 設定だけで、判定がない |
| `ShiftManagementApplication` | 除外 | `main` だけ |
| テンプレート（HTML）・`app.js` | 総合テスト（5章）で確かめる | JaCoCo では測れない |

Lombok が作ったメソッドをカバレッジから外すため、プロジェクトの一番上に `lombok.config` を置きます（10_基本設計書 7章）。

```properties
# Lombok の設定（97_テスト計画書 2.2）
config.stopBubbling = true
lombok.addLombokGeneratedAnnotation = true
```

## 3. テストの環境と書き方

### 3.1 テスト用の設定

`src/test/resources/application-test.yml`：

```yaml
# テスト用の設定（97_テスト計画書 3.1）。@ActiveProfiles("test") で読み込む
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/shift_test?connectionTimeZone=%2B09:00&forceConnectionTimeZoneToSession=true&characterEncoding=UTF-8
    username: shift_app
    password: ${DB_PASSWORD}
  thymeleaf:
    cache: true
logging:
  level:
    jp.numajo.fgroup.shift: INFO
app:
  backup:
    dir: "${java.io.tmpdir}/shift-management-test-backup"
```

- DB は `shift_test`（96_環境構築手順書 6.1 で作る）。テストの起動時に Flyway が V1・V2 を流します（40_DB設計書 9章）。
- DB を使うテストクラスには `@SpringBootTest` と `@ActiveProfiles("test")` を付けます。画面のテストはさらに `@AutoConfigureMockMvc`。
- 日時を固定するテストは、`@MockitoBean Clock clock` ではなく、`@TestConfiguration` で `Clock.fixed(Instant.parse("2026-10-20T00:00:00Z"), ZoneId.of("Asia/Tokyo"))` を `@Primary` の Bean にします（30-01 `ClockConfig` を上書きする）。
- DB のデータ：`@Transactional` を付けたテストは終わると元に戻ります。付けないテスト（ログインの流れなど）は `@BeforeEach` で必要な値を入れ直します。テスト同士で順番に頼ってはいけません。

### 3.2 組み合わせ表（条件網羅・複数条件網羅）

条件が2つ以上ある判定は、テストクラスの Javadoc に組み合わせ表を書き、表の1行を1つのテスト（または `@ParameterizedTest` の1行）にします。

**例1：受付中かどうか（`PeriodService#isAcceptingRequests`）**

判定：`status == OPEN && !now.isAfter(deadlineAt)`（条件A：状態が OPEN、条件B：期限を過ぎていない）

| No. | A | B | 判定 | テストの値 |
| --- | --- | --- | --- | --- |
| 1 | 真 | 真 | 真（受付中） | OPEN、now＝期限ちょうど 10/31 23:59:59 |
| 2 | 真 | 偽 | 偽 | OPEN、now＝11/1 0:00:00 |
| 3 | 偽 | 真 | 偽 | CLOSED、now＝10/31 12:00 |
| 4 | 偽 | 偽 | 偽 | PUBLISHED、now＝11/1 0:00:00 |

- C2：A・B それぞれに真と偽がある（No.1〜4）。MCC：2² ＝ 4 通りすべて。
- No.3・4 は、短絡評価で B を見ないが、組み合わせとしてテストする。

**例2：ログイン中に無効にされた人（`UserActiveCheckFilter`）**

判定：`auth != null && auth.getPrincipal() instanceof LoginUser && !active`（A・B・C）

| No. | A：ログイン情報がある | B：LoginUser | C：無効 | 判定 | 結果 |
| --- | --- | --- | --- | --- | --- |
| 1 | 真 | 真 | 真 | 真 | `/login?disabled` |
| 2 | 真 | 真 | 偽 | 偽 | そのまま次へ |
| 3 | 真 | 偽（匿名ユーザー） | － | 偽 | そのまま次へ |
| 4 | 偽 | － | － | 偽 | そのまま次へ |

- 「－」はありえない組み合わせ：B が偽（匿名）なら利用者がいないので C は決まらない。A が偽なら B・C も決まらない。表の下に「除外：A偽のときB・Cは評価できない」と理由を書く。
- C の「真」は「ユーザーが消えている」と「`is_active = FALSE`」の2通りを両方テストする（`orElse(false)` の分岐）。

**書き方の決まり**

- 組み合わせ表は、20_詳細設計書の「テストの観点」の表を元に作ります。観点の表だけで組み合わせが足りないときは、足してください（設計書を直す必要はありません）。
- 入力チェック（Bean Validation）の境界値は、「最小−1・最小・最大・最大＋1」の4つを必ず入れます（例：パスワード 7・8・64・65文字）。
- 日付の境界は「前日・当日・翌日」、時刻の境界は「1秒前・ちょうど・1秒後」を入れます。

### 3.3 テストクラスの書き方

```java

    private ShiftRequestService shiftRequestService;

    @Test

        // 確認（Assert）
    }

```

| 項目 | 決まり |
| --- | --- |
| クラス名 | 対象クラス名＋`Tests`。パッケージは対象と同じ |
| メソッド名 | 日本語で `条件_期待する結果`（91_コーディング規約 2.1） |
| 中身の並び | 準備 → 実行 → 確認 の3つに分け、空行で区切る |
| 確認のしかた | AssertJ（`assertThat(…)`）を使う。例外は `assertThatThrownBy(…).isInstanceOf(BusinessException.class).extracting("messageCode").isEqualTo("E1303")` |
| モック | 単体テストは `@ExtendWith(MockitoExtension.class)`、`@Mock`、`@InjectMocks`。`@SpringBootTest` の中では `@MockitoBean` |
| 呼び出しの確認 | 呼んだかどうかが仕様のとき（お知らせを作る、操作ログを残す）は `verify(…)` で回数まで確かめる |
| 画面のテスト | `mvc.perform(post("/staff/requests").with(csrf()).with(user(loginUser))…)` の形。CSRF なしの POST が 403 になることも1件入れる |

### 4.3 Windows での ProcessRunner のテスト

検証用プロジェクトの `ProcessRunnerTests` は Linux の `sh` で確かめたものです。班員のPCは Windows なので、同じ5つの観点を `cmd`・`powershell` で書いた次のコードを使います。**このコードは Windows でまだ動かしていません。** 栗原さんが最初のテスト実行（6章）で5件とも通ることを確かめ、通らなければ新井に連絡します。

ファイル：`src/test/java/jp/numajo/fgroup/shift/util/ProcessRunnerTests.java`

```java
package jp.numajo.fgroup.shift.util;

import static org.assertj.core.api.Assertions.assertThat;

import java.time.Duration;
import java.util.List;
import java.util.Map;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.condition.EnabledOnOs;
import org.junit.jupiter.api.condition.OS;

import jp.numajo.fgroup.shift.dto.ProcessResult;

/**
 * ProcessRunner の単体テスト（Windows の cmd・powershell で確認する）。
 */
@EnabledOnOs(OS.WINDOWS)
class ProcessRunnerTests {

    /** 5秒待つコマンド（cmd の timeout は入力待ちになるため powershell を使う） */
    private static final List<String> SLEEP_5_SECONDS =
            List.of("powershell", "-NoProfile", "-Command", "Start-Sleep -Seconds 5");

    private final ProcessRunner runner = new ProcessRunner();

    @Test
    void 成功_環境変数が渡る() {
        ProcessResult r = runner.run(List.of("cmd", "/c", "echo %MYSQL_PWD%"), Map.of("MYSQL_PWD", "secret"),
                Duration.ofSeconds(5));

        assertThat(r.exitCode()).isZero();
        assertThat(r.timedOut()).isFalse();
        assertThat(r.output().trim()).isEqualTo("secret");
    }

    @Test
    void 失敗_終了コードとエラー出力() {
        ProcessResult r = runner.run(List.of("cmd", "/c", "echo err 1>&2 & exit /b 3"), Map.of(),
                Duration.ofSeconds(5));

        assertThat(r.exitCode()).isEqualTo(3);
        assertThat(r.output().trim()).isEqualTo("err");
    }

    @Test
    void コマンドがない() {
        ProcessResult r = runner.run(List.of("C:\\no\\such\\command.exe"), Map.of(), Duration.ofSeconds(5));

        assertThat(r.exitCode()).isEqualTo(-1);
        assertThat(r.timedOut()).isFalse();
    }

    @Test
    void 時間切れ() {
        ProcessResult r = runner.run(SLEEP_5_SECONDS, Map.of(), Duration.ofMillis(300));

        assertThat(r.timedOut()).isTrue();
        assertThat(r.exitCode()).isEqualTo(-1);
    }

    @Test
    void 割り込み() {
        Thread.currentThread().interrupt();

        ProcessResult r = runner.run(SLEEP_5_SECONDS, Map.of(), Duration.ofSeconds(5));

        assertThat(r.output()).isEqualTo("interrupted");
        assertThat(Thread.interrupted()).isTrue();
    }
}
```

`BackupService` のテストでは `ProcessRunner` を `@Mock` にし、「成功（終了コード0・ファイルあり）」「終了コード0以外」「時間切れ」「ファイルの大きさ0」「同時に2回（E4402）」を確かめます（20-SA-04 のテストの観点）。本物の `mysqldump` を動かすのは総合テスト（5章 No.12）だけです。
