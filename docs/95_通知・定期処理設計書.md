## 1. 一覧

### 1.1 定期処理

| ID | 名前 | いつ | クラス・メソッド（scheduler） | 中身（Service） |
| --- | --- | --- | --- | --- |
| BT-01 | 募集期間の作成 | 毎日 0:05、起動したとき | `PeriodScheduler#createUpcoming` | `PeriodService#createUpcomingPeriods(LocalDate today)` |
| BT-02 | 募集期間の締切 | 毎日 0:00:30、起動したとき | `PeriodScheduler#closeExpired` | `PeriodService#closeExpiredPeriods(LocalDateTime now)` |
| BT-03 | 締切のお知らせ | 毎日 9:00（起動したときは動かさない） | `DeadlineNotificationScheduler#sendReminders` | `NotificationService#sendDeadlineReminders(LocalDate today)` |

- 定期処理を動かすため、起動クラスに `@EnableScheduling` を付けます（30-01）。
- cron はすべて `zone = "Asia/Tokyo"` を付けます。
- scheduler のクラスには「いつ呼ぶか」だけを書き、中身は Service に書きます（テストで日時を渡して確かめられるようにするため）。コードは 30-08 4章に全文があります。
- 起動したときは `PeriodScheduler#onStartup`（`ApplicationReadyEvent`）が **BT-02 → BT-01** の順に1回動かします。新井のPCを夜に切っていて 0:05 に動かなかった日があっても、起動すれば追いつきます。

### 1.2 お知らせ（通知）

メールは使わず、すべて `notifications` テーブルに入れるアプリ内のお知らせです。

| 種類（`NotificationType`） | いつ作るか | 作る処理 | 宛先 | 件名 | 本文 | link_url |
| --- | --- | --- | --- | --- | --- | --- |
| DEADLINE | 毎日 9:00 | BT-03（4章） | 未提出の有効なバイト（本人が選んだ日だけ） | N0001 | N1001 | `/staff/requests?periodId={期間ID}` |
| PUBLISHED | 店長が公開した | 20-SM-06 3.6 | 有効なバイト全員 | N0002 | N1002 | `/staff/shifts?periodId={期間ID}` |
| CHANGED | 公開後に割当を追加・削除した、欠勤登録した | 20-SM-06 3.3〜3.5、20-SM-07 3.3 | 変わったバイト本人 | N0003 | N1003（追加）、N1004（外れた）、N1005（欠勤） | `/staff/shifts?periodId={期間ID}` |
| VACANCY | 欠勤登録した | 20-SM-07 3.3 | 欠員通知の相手（20-SM-07 3.4） | N0004 | 店長が入力した文（`noticeMessage`） | `/staff/home` |
| CHAT | チャットを送った | 20-SB-06、20-SM-11 | バイトが送った → 有効な店長全員、店長が送った → そのバイト | N0005 | メッセージの先頭50文字 | バイト宛て `/staff/chat`、店長宛て `/manager/chats/{バイトのユーザーID}` |

件名・本文のコードと引数は 93_メッセージ一覧 3章。時間指定の割当では、枠名の代わりに N1006（「時間指定 13:00〜22:00」）を使います。

## 2. BT-01 募集期間の作成

### 2.1 何をするか

「今月」と「来月」の前半（1日〜15日）・後半（16日〜末日）の4期間のうち、`shift_periods` にないものを作ります。

### 2.2 手順（`PeriodService#createUpcomingPeriods(LocalDate today)`、`@Transactional`）

1. `first = today.withDayOfMonth(1)`（今月1日）。
2. 開始日の候補を、この順に4つ作る：`first`、`first.withDayOfMonth(16)`、`first.plusMonths(1)`、`first.plusMonths(1).withDayOfMonth(16)`。
3. 候補ごとに：
   1. `ShiftPeriodRepository#existsByStartDate(start)` が true → 何もしない。
   2. 終了日：開始日が1日なら `start.withDayOfMonth(15)`、16日なら `start.with(TemporalAdjusters.lastDayOfMonth())`。
   3. 期限：`PeriodService.deadlineOf(start)`
      - 開始日が1日 → `start.minusMonths(1).withDayOfMonth(15).atTime(23, 59, 59)`
      - 開始日が16日 → `start.minusMonths(1).with(TemporalAdjusters.lastDayOfMonth()).atTime(23, 59, 59)`
   4. 状態：期限の日付が `today` より前（`deadline.toLocalDate().isBefore(today)`）なら `CLOSED`、そうでなければ `OPEN`。
      - 初めて起動した日や、PCを長く切っていたあとに、すでに期限を過ぎた期間を OPEN で作らないためです。
   5. `published_at` は NULL。`save` する。作った数を1増やす。
4. 作った数を返す。scheduler が `log.info("BT-01 募集期間を{}件作成しました", count)` を出す。

`start_date` には一意制約があるので、万一2つ同時に動いても同じ期間が2つできることはありません（2つ目は例外になり、ログに出て、翌日また動く）。

### 2.3 例（令和8年10月21日に初めて起動した場合）

| 開始日 | 終了日 | 期限 | 状態 |
| --- | --- | --- | --- |
| 2026-10-01 | 2026-10-15 | 2026-09-15 23:59:59 | CLOSED |
| 2026-10-16 | 2026-10-31 | 2026-09-30 23:59:59 | CLOSED |
| 2026-11-01 | 2026-11-15 | 2026-10-15 23:59:59 | CLOSED |
| 2026-11-16 | 2026-11-30 | 2026-10-31 23:59:59 | OPEN |

11月1日の 0:05 には、12月の2期間（期限 11/15、11/30）が OPEN で増えます。

## 3. BT-02 募集期間の締切

### 3.1 手順（`PeriodService#closeExpiredPeriods(LocalDateTime now)`、`@Transactional`）

1. `ShiftPeriodRepository#findByStatusAndDeadlineAtBefore(PeriodStatus.OPEN, now)` で、期限を過ぎた受付中の期間を取る。
2. それぞれ `status = CLOSED` にする（JPA の変更検知で UPDATE される）。
3. 締めた数を返す。scheduler が `log.info("BT-02 募集期間を{}件締め切りました", count)` を出す。

### 3.2 決まり

- `now` が期限ちょうど（23:59:59）のときは締めません（`Before` は「より前」なので）。希望の受付も `!now.isAfter(deadlineAt)` なので、両方とも「期限の時刻までは受け付ける」でそろっています。
- 0:00:00〜0:00:30 の間は、状態はまだ OPEN ですが、受付の判定（10_基本設計書 6.1）で日時も見るため、提出はできません。
- 締めたときに、お知らせは作りません（店長はダッシュボードで提出状況を見る。20-SM-01）。

## 4. BT-03 締切のお知らせ

### 4.1 何をするか

期限まで「0日（当日）・1日・3日・7日」のうち、バイトが SB-05 で選んだ日の 9:00 に、まだ希望を出していない人へ DEADLINE のお知らせを作ります。新しく登録したバイトは「1日前・3日前」が選ばれた状態です（`NotificationSettingService.DEFAULT_DAYS`）。

### 4.2 手順（`NotificationService#sendDeadlineReminders(LocalDate today)`、`@Transactional`）

```
count = 0
for d in NotificationSettingService.DAYS_OPTIONS（0, 1, 3, 7 の順）:
    target = today.plusDays(d)
    periods = ShiftPeriodRepository#findByStatusAndDeadlineAtBetween(
                  OPEN, target.atStartOfDay(), target.atTime(23, 59, 59))
    periods が空 → 次の d へ
    userIds = NotificationSettingRepository#findUserIdsByDaysBefore(d.byteValue())
    userIds が空 → 次の d へ
    staffs = UserRepository#findAllById(userIds) のうち、role == STAFF かつ active == true の人（ID の昇順）
    for period in periods:
        submitted = Set.copyOf(RequestSubmissionRepository#findUserIdsByPeriodId(period.id))
        link = "/staff/requests?periodId=" + period.id
        for staff in staffs:
            submitted に staff.id がある → 次へ
            NotificationRepository#existsByUserIdAndTypeAndLinkUrlAndCreatedAtGreaterThanEqual(
                staff.id, DEADLINE, link, today.atStartOfDay()) が true → 次へ（今日すでに送った）
            create(staff, DEADLINE,
                   件名 = getMessage("N0001"),
                   本文 = getMessage("N1001", [DateTimeUtil.period(start, end), DateTimeUtil.dateTime(deadlineAt)]),
                   link)
            count++
return count
```

- 本文の例：「11/16〜11/30 の希望がまだ提出されていません。期限は 2026/10/31 23:59 です。」
- 件名・本文は `MessageSource#getMessage(コード, 引数, Locale.JAPAN)` で作ります。
- scheduler が `log.info("BT-03 締切のお知らせを{}件作成しました", count)` を出します。

### 4.3 決まり

| 項目 | 決まり |
| --- | --- |
| 二重に送らない | 同じ人・同じ種類・同じ link_url のお知らせが、今日の 0:00 以降にあれば作らない。アプリを 9:00 をまたいで再起動しても、手で2回呼んでも1通だけになる |
| 0日前 | 期限の日の 9:00 に送る（その日の 23:59:59 まで出せる） |
| 期限を過ぎた期間 | OPEN でなければ（BT-02 で CLOSED になっていれば）送らない |
| 無効なバイト・店長・管理者 | 送らない（設定の行が残っていても） |
| 提出を取り消した人 | `request_submissions` に行がないので「未提出」として送る |
| 9:00 にアプリが動いていなかった日 | その日の分は送らない（あとから追いかけない）。起動時にも動かさないのは、夜中に起動して朝前にお知らせが出るのを防ぐため。課題期間中は 9:00 前にアプリを起動しておく運用にする（96_環境構築手順書 9章） |

## 5. お知らせを作る共通の決まり

| 項目 | 決まり |
| --- | --- |
| 作るメソッド | `NotificationService` の `private void create(User to, NotificationType type, String title, String body, String linkUrl)` だけ。ほかのクラスから `NotificationRepository#save` を直接呼ばない |
| トランザクション | `notifyPublished`・`notifyChanged`・`notifyVacancy`・`notifyChat` は `Propagation.MANDATORY`（業務処理と同じトランザクション。業務処理が失敗したらお知らせも残らない） |
| 長さ | 件名は100文字、本文は500文字で切る（列の長さに合わせる） |
| `created_at` | DB の既定値（`CURRENT_TIMESTAMP`）。Java から入れない |
| `read_at` | NULL（未読）で作る。開いたら SC-02 で今の日時を入れる |
| link_url | アプリの中のパスだけ（1.2 の表）。開くときも確かめる（94_セキュリティ設計書 3.7） |
| 自分あて | 自分の操作で自分にお知らせは作らない（例：店長がチャットを送っても、送った店長には作らない） |
| 消すとき | 消さない（SC-02 は新しい100件だけを表示する） |
